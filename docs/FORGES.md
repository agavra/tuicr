# Forge integration (tuicr)

Reference for everything under `src/forge/`. Loaded on demand from `AGENTS.md`; read it before touching `src/forge/`, PR mode (`pr_info`, `spawn_pr_*`), submit/session lifecycle or PR-related gotchas. Gotchas: `F*` = shared forge/PR, `G*` = backend-specific; general ones are numbered in `AGENTS.md`.

Everything under `src/forge/`. Backends shell out to `gh` (GitHub), `glab` (GitLab), `tea` (Gitea), `bkt` (Bitbucket Cloud only), use REST with a PAT or `az rest` (Azure DevOps), or the Gerrit REST API (no CLI exists).

**Detection** (`parse_any_remote_url`, in order): Bitbucket (Cloud incl. SSH hosts), GitLab (host contains `gitlab`, or matches the *hostname* of `glab config get host`, often written as a URL), Azure, Gitea (host contains `gitea` or matches a `tea logins list --output json` login; forks like Forgejo deliberately not matched by name), Gerrit, then GitHub. **GitHub stays last**: its parser accepts any host and would claim everything. Bitbucket Data Center (REST 1.0) is unsupported and not claimed.

**ForgeBackend** (`src/forge/traits.rs`) contracts that are not obvious from signatures:
- `list_pull_requests`: `last_commit_at` is optional. GitHub fills it with one extra GraphQL `commits(last: 1)` query per page (never `gh pr list --json commits`, which pulls up to 100 commits per PR) and leaves `None` on failure; others leave `None`.
- `get_pull_request_info`: GitHub fetches review/merge/check fields in one `gh pr view`; others default to `PullRequestInfo::from_details`.
- `PullRequestReviewStatus` rows are *effective votes*, not the latest response: on Gitea a later comment-only review never replaces an earlier approval/change request (a newer decisive review does), dismissed reviews are ignored, and `submitted_at` is the effective row's time. Gitea info uses one detail GET.
- `get_pull_request_diff` / `get_pull_request_commit_range_diff` return structured `FilePatch` values (path/status from API metadata paired with patch bodies). Range diffs: `start_sha` is the parent of the first selected commit, `end_sha` the last.
- `list_pull_request_review_metadata`: best-effort viewer login + review commit OIDs, used to preselect commits since the viewer's latest review. GitLab combines `/user`, MR diff versions, approvals, discussions; Bitbucket reads `participants` (account UUIDs, no commit OIDs).
- `resolve_diff_base_sha`, `fetch_file_lines`, `list_review_threads`, `create_review`, `list_pull_request_commits`.

**Async pattern** (`spawn_pr_open`/`spawn_pr_reload`/`spawn_pr_submit`): snapshot inputs on the main thread (no `&App` across the spawn); a thread returns only `Send` data over an `mpsc` channel drained by `poll_*_events()`; the main-thread `finish_*` parses diffs and builds the `ReviewSession`, because `SyntaxHighlighter` is not `Send`. In-flight requests carry identity `(repo, PR#, head SHA)`; a late result for a different PR is discarded (otherwise open/submit results would apply lifecycle writes to the wrong comments). The check is against the *live* `diff_source` (`App::pr_result_is_current`), never the in-flight snapshot, and covers reload and range-reload results too (range also needs `commit_selection_range == request.range`). `SubmitInFlightState::pr_head_sha` is the session head, `head_sha_snapshot` the subset `commit_id`. A successful receipt for a PR no longer open is written to that PR's own session, not dropped (else its drafts post twice). Entering a PR and widening to all commits cancel in-flight reload/range state.

**Session key and lifecycle**: `PrSessionKey { repository, number, head_sha }`. Same PR + head = same session (drafts reattach). A new head = a new session seeded best-effort from the previous head's session of the same repository (host included) and PR; unchanged files keep reviewed marks and drafts. `Comment.lifecycle`: `local_draft` (editable), `pushed_draft` (submitted as Draft, still a pending GitHub review), `submitted` (locked). Success transitions atomically per the response; a failure leaves `local_draft`, except comments a multi-request forge already posted (G12), which lock even when the failure arrives after the PR was switched (the receipt goes to the originating session).

**Submit pipeline** (`src/forge/submit.rs`): preflight maps each comment to an inline anchor (path + line + side) by walking displayed hunks → unmappable ones go to the resolver modal (move to summary, or omit) → confirmation modal (warns if head advanced) → post via `gh api --input -` (stdin: multi-comment payloads exceed CLI arg limits; see `GhCommandRunner::run_with_stdin`).

### Gotchas (forge and PR mode)

F1. **`gh pr diff` must NOT use `--patch`** (per-commit mbox patches → duplicate file entries). Plain `gh pr diff` is cumulative. Test: `should_not_pass_patch_flag_to_gh_pr_diff`.
F2. **GraphQL thread anchors** (`path`, `line`, `originalLine`, `diffSide`) live on `PullRequestReviewThread`, not the comment; asking the comment is a schema error.
F3. **`gh api` writes the response body to STDOUT on non-2xx**; STDERR has only the short status line. The error formatter combines both.
F4. **`apply_initial_load(Err(..))` is a no-op when the tab is already `Loaded`** (only `Loading → Error`). For transient reload/submit errors use `App::set_error()`.
F5. **Subset-mode `commit_id`**: for a strict subset of PR commits the payload's `commit_id` is `pr_commits[start_idx].oid` (the newest selected). The cumulative head yields a misleading 422 `commitOID is not part of the pull request`.
F6. **`base_sha` means the merge base, not the base-branch tip.** `baseRefOid` (GitHub), `lastMergeTargetCommit` (Azure), `destination.commit.hash` (Bitbucket) can report the tip, but a three-dot patch's old side is `merge-base(base, head)`. `resolve_diff_base_sha` reconciles it once in `fetch_pr_data` before fetching the patch (GitHub/Bitbucket: local first, then compare/merge-base API; Azure: local). GitLab, Gitea already report the merge base; Gerrit uses the change's parent. Best-effort: `None` keeps the reported base. Same-head reloads must refresh `diff_source.pr.base_sha` too (retargeted PRs).
F7. **`fetch_pr_data` fans out** after `get_pull_request_info` and `resolve_diff_base_sha`: `get_pull_request_diff`, `list_pull_request_commits`, `list_pull_request_review_metadata` run concurrently via `forge::join` (scoped threads). Backends must be `Sync` (`create_forge_backend` returns `Box<dyn ForgeBackend + Sync>`) and test fakes record via `Mutex`/atomics, not `RefCell`/`Cell`. Error precedence stays sequential: a diff error fails the open; commit/review-metadata failures degrade to empty. GitHub's diff fetches `pulls/N/files` and `gh pr diff` the same way, and a file-list error wins. The head can advance mid-fan-out, so `fetch_pr_data` re-reads `get_pull_request_info` afterwards; a different `head_sha` retries the whole fetch once, then errors (never keep metadata for head A with head B's diff).
F8. **PR open reads every changed file's line count, so batch it** (`populate_file_line_count_cache` → `ForgeContextProvider::file_line_counts` → `ForgeBackend::file_line_counts`, never a per-file loop). GitHub: one `git cat-file --batch` over local blobs (`vcs::git::cli::read_git_objects`), then one GraphQL `object(expression:)` query per 50 files; truncated/non-text blobs and failed-query blobs fall back to one REST call each. `read_git_objects` feeds stdin from a thread: a PR can list more specs than a pipe buffer holds and writing first would deadlock. Other backends use the one-at-a-time default.
F9. **Commit messages are shown but are not PR files.** `App::insert_commit_message_if_single` puts a `Commit Message (<short oid>)` pseudo-file at `diff_files[0]` when one commit is selected/reviewed; every PR path assigning `self.diff_files` must call `App::rebuild_pr_diff_view(insert_message)` (message, sort, expand, annotate), as local paths do. Exception: an initial open (`enter_pr_diff_mode`, CLI startup) with a strict selection that starts a range reload passes `false`, so no message sits above the cumulative diff while the range loads or fails; range-reload finish and cached-full restore pass `true`. Never forbid messages for strict selections globally. Never ask the forge about that path: `populate_file_line_count_cache` omits it (F8), and submit preflight must never pass an `is_commit_message` file to `map_comment` (the forge rejects the path and the whole review). Preflight instead walks `pr_commits` via `DiffFile::commit_message_path` and sends them to the resolver as `UnmappableReason::CommitMessage` (Gerrit's inline `/COMMIT_MSG` is unimplemented). `PullRequestCommit::body` holds the whole message or `None`: Azure truncates `comment` (`commentTruncated`), so that backend reads local clone, then API. A same-head reload keeps a narrowed selection (`apply_same_head_pr_reload`) only while PR identity is unchanged: if the diff base changes, or a non-empty incoming commit list differs in order/membership, `reset_pr_selection_to_cumulative` installs the new cumulative diff, drops the in-flight range reload, clears index-keyed caches, selects all commits explicitly (`Some((0, len-1))`, never `None`, so removed commits' comments stay hidden) and persists that; an empty incoming list means membership unknown (F7) and keeps the existing lists. When a head moves, `reviewed_state_carried_forward` also carries each still-present commit's `Commit Message` review (marks, unlocked drafts); the exact-head session wins.
F10. **`e` in PR mode must not resolve against the working tree.** `PrNoopVcs` has no local VCS, and `vcs_info.root_path` is synthetic (`forge:host/owner/repo`); the checkout may be on any branch or absent. Use `App::pr_editor_target`: it reads the reviewed revision (local blob via `forge::local_git::read_blob`, else `ForgeBackend::fetch_file_content`) and hands over the worktree file only if content matches. `fetch_file_lines` runs `slice_context_lines`, which expands tabs, so it is never byte-faithful: anything writing content to disk must use `fetch_file_content`.

Backend-specific:

G1. **Gerrit's patch endpoint cannot be paired positionally with its file list**: `/revisions/{id}/patch` follows git's rename-aware diff order, `/files/` is path-sorted (renames would mis-zip; AGENTS.md gotcha 1 forbids reading paths from patch text). The backend builds diffs from a local clone via `git diff base..head` after fetching `refs/changes/NN/CCCC/P` (writes `FETCH_HEAD` only, moves no ref).
G2. **Gerrit has no reserved hostname**: `parse_gerrit_remote_url` gates on SSH port `29418`, a `GERRIT_URL` naming the host, or a hostname containing "gerrit"; it must sit ahead of the GitHub catch-all and behind every other host-gated parser.
G3. **A Gerrit project is a path**: `ForgeRepository::gerrit` packs the parent path into `owner` and the last segment into `name`, falling back to the *host* as owner for single-segment projects (an empty owner makes slug `ge:/repo/pr/1`, which `parse_pr` rejects). `gerrit_project()` is the only way back.
G4. **Gerrit's review-requested toggle uses `attention:self -owner:self`, not `reviewer:self`** (which also matches changes already voted on and handed back). The one deliberate divergence from shared semantics; needs Gerrit 3.3+ for that toggle alone.
G5. **Gerrit `/changes/{N}/comments` returns published comments only**; drafts are at `/changes/{N}/drafts` (`author` unset). `:submit draft` marks local copies `PushedDraft` and the refetch runs `prune_locked_comments`, so a backend that cannot read its drafts back deletes the only copy. Read `/drafts` too. The same holds for every backend: whatever `SubmitEvent::Draft` posts must come back through `list_review_threads`/`list_review_summaries` (Gitea: don't filter PENDING summaries; GitLab: read `/draft_notes`, inline drafts become `is_draft` threads, general ones `Pending` summaries).
G6. **Self-hosted Azure DevOps Server/TFS is opt-in by hostname**: `parse_azure_remote_url` claims it only when the host equals `AZURE_DEVOPS_SERVER_URL`'s (ahead of the GitHub catch-all). `collection/project` is packed into `owner` with the real host kept (cloud hosts normalize to `dev.azure.com` and drop `DefaultCollection`). Virtual directories can make the collection multi-segment, so `azure_coords` splits `owner` at the *last* `/`.
G7. **`tea api` exits 0 for every HTTP response**, body on stdout even for 404. The Gitea backend passes `-i` (status line and headers on stderr) and reads the status there, hence `run_command_streams`, not `run_command_output`.
G8. **Gitea clamps `limit` to `MaxResponseItems`** (default 50). Paginate off `X-Total-Count`, falling back to reading until a page is short *relative to the first page's size*, never relative to the requested limit. A truncated `/pulls/{n}/files` turns into a hard "metadata records but N patch blocks" mismatch because it is paired positionally with the `.diff`.
G8a. **Pagination is finite and refuses rather than truncates.** Bitbucket collections stop at 100 pages (`MAX_PAGES`), GitLab MR commits at 10,000 (`MAX_COMMIT_PAGES` x 100), Gitea collections at 200 pages (`MAX_PAGES`, which also covers the PR picker's look-ahead row). Exceeding a bound returns `TuicrError::ForgeLimit`, never a partial `Ok`. `fetch_pr_data` treats commits and review metadata as best-effort (failures become empty) *except* `ForgeLimit`, which fails the PR open with that message so the user is never shown zero commits for a large PR. Any new bounded loop must return `ForgeLimit` and nothing may `unwrap_or_default` it away.
G9. **Gitea reports a mode-only change as status `unchanged`** yet emits a `diff --git` block: keep the file in the metadata list or later files pair wrongly.
G10. **GitLab relative-URL install**: `glab` already prefixes the subfolder, so strip it from the project id, not from `owner`. A clone URL cannot tell `<sub>` from a top-level group, so it lands in `ForgeRepository.owner`; `owner` keeps it because it is persisted in session slugs and `PrSessionKey`, parsed at three sites (including `owner/repo#iid`, with no host to look up), and the hostname-only parser must not spawn `glab` (`resolve_owner_repo` runs on every session save). `GitLabGlabBackend::project_path`/`api_project` are the only route from a `ForgeRepository` to an API project path; `repo_arg` stays subfolder-ful on purpose (`glab` strips its configured subfolder when parsing a `--repo` URL). The subfolder comes from `glab` (`GITLAB_SUBFOLDER`, else `glab config get subfolder --host`), never tuicr config, memoized per host in a `Mutex` (F7). Stripping is segment-aligned, once, and never leaves fewer than two segments. Only the *hostname* of `glab config get host` is compared; its path is not a subfolder source.
G11. **Gerrit invariants.** A root revision has no parent, so `base_sha` can be `EMPTY_TREE_SHA`; `revision_present` must accept it both before and after the patch-set fetch (a real commit check on it always fails). A thread's resolved state comes from its *latest* reply, not its root comment, so a reopening reply makes it unresolved.
G12. **GitLab, Bitbucket and Azure post a review as several requests, so a failure can land midway.** `create_review` records what went out in `SubmitReceipts` and returns it in `TuicrError::PartialSubmit` (`into_error`); `lock_partially_submitted` locks those comments so a retry never reposts them, and a new sequential post must be recorded there. Locked comments are excluded from the guard, body, `review_comment_ids` and confirm label, so a bare `RequestChanges` retry is allowed on these three (not GitHub, which rejects an empty one). Azure resolves the voter *and* every inline thread's `pullRequestThreadContext` (iteration whose `sourceRefCommit` is `request.commit_id`, `changeTrackingId` from its changes, equal first/second iteration, except Left comments of a strict subset, which start at the iteration whose head is `request.base_commit_id` or are rejected unless it is the common base) *before* posting, so an unanchorable commit fails with nothing posted; a PR with no iterations posts without a context; GitLab's `/approve` maps only an HTTP 401 or 403 to "not an eligible approver" (CLI login errors keep the auth message).
G13. **PR session identity includes the forge host, for NEW sessions only.** A new session's file is `fnv1a("pr2|<forge>|<host>|<owner>/<repo>|<n>|<head>")` (`new_pr_target`), its manifest bucket `gh:o/r/pr/N` on the forge's default host (`slug::default_host`; Gerrit has none) or `gh:o/r/pr/N@<host>` elsewhere, and its manifest entry carries `host`. `slug::normalized_host` (lowercase, trailing dots trimmed, port kept, no `www.` aliasing) is the only normalizer: hash, suffix, manifest field and every comparison (`same_pr_identity`, never raw `ForgeRepository ==`). `storage::resolve_pr_target` is the only place choosing the file: the new file if it exists; else the legacy `fnv1a("pr|<hostless slug>|<head>")` file when it parses and holds an equal key (it keeps its path and hostless manifest entry forever); else the new file. Legacy files are never moved, rewritten, normalized or deleted by implicit paths, and a legacy file that is missing or does not parse is "no holder" (`read_legacy_holder`), but any other I/O error fails closed, so a transient failure cannot fork a session into a second file. Every occupied target is verified (full key) before a write; a cached path or `SessionRef` that identity resolution no longer names fails with `TuicrError::SessionTargetChanged` and writes nothing; the `App` re-resolves its cached path on the next same-head reload (`reresolve_pr_session_path`), keeping its merge snapshot so the new file's contents merge in as external changes. App-level key checks use `same_pr_identity` plus head, never raw key equality. `review list` emits the `@host` slug for legacy non-default-host entries (derived from the file's key), so list -> `--session` resolves. Selectors: a hostless slug reaches only default-host sessions, `@host` reaches that host; legacy `None`-host manifest entries are trusted only when the file's own host matches, so the startup marker of a legacy GHE session is `gh:o/r/pr/N@<host>` while its manifest key stays hostless. `load_pr_session` falls back to the resolved file when the manifest has no entry (crash between file and manifest write) and re-indexes. Deleting a session prunes its manifest entries by path across all buckets. **Not fixed (out of scope, see p_persist_writeback):** drafts an older binary already overwrote, two legacy holders of one hash, a hostless legacy selector among several legacy holders, manifest rebuild/repair, old binaries not seeing new-hash files after a downgrade.
